# BizzaGameAnalytics 编辑器体验验收文档

## 1. 验收目标

本文档用于在真实游戏已经接入 `BizzaGameAnalytics` 后，通过 Unity Editor 正常体验游戏，
再由 AI 分析日志，判断各类业务打点是否确实被触发、是否交给底层 SDK，以及是否获得服务器
成功响应。

用户不需要手动调用打点接口，也不需要逐条检查 Console。用户只需要进入 Play Mode 正常
体验希望覆盖的玩法，AI 负责读取和分析本次运行日志。

## 2. 四层证据必须分开

日志验收分为四层，不能混为一谈：

| 层级 | 主要日志 | 能证明什么 |
|---|---|---|
| 1. 业务触发 | `[BizzaGameAnalytics] event_accepted`；启动漏斗使用 `[BizzaAnalytics] lifecycle_event=...` / `load_stage_event=... accepted=True` | 调用已通过校验并进入对应队列 |
| 2. 底层交接 | `[BizzaGameAnalytics] event_handed_off` | 普通业务事件已调用 `BizzaAnalyticsAgent.Track`；启动漏斗直接在底层产生，无此日志 |
| 3. 底层处理 | `[BizzaAnalytics] track(user) event=...` | 事件已进入底层 Track 处理路径；还需确认没有紧随其后的提交异常 |
| 4. 网络成功 | `[BizzaAnalytics] send(result) ... ok=True status=2xx` | 当前批次请求得到服务器成功响应 |

只有第 4 层能作为端到端网络成功证据。`lifecycle_event accepted=True`、`event_accepted` 和
`event_handed_off` 都不能描述成“服务器已经收到”。服务器后台最终是否按预期入库，仍建议
至少人工核对一次。

## 3. 测试前提

开始体验前，由接入或验收 AI 完成以下准备：

1. 已按照 `Assets/BizzaAnalytics/BizzaGameAnalytics/AI接入文档.md` 完成真实业务回调接入。
2. `BizzaGameAnalytics.TrackGameLoadComplete()` 已接到真正的全部加载完成回调。
3. `Assets/StreamingAssets/BizzaAnalytics.bytes` 属于当前产品、内置正确 AppId 且可以正常解析。
4. 统一配置需要联网，并允许访问配置中的上报服务。
5. 如需查看底层详细日志，应在统一配置中开启 `verbose_log`；否则只能验证前两层。
6. Unity Console 应开启普通日志、Warning 和 Error 显示。

当前模板工程所有环境统一使用正式配置；接入其他产品后应以目标产品重新生成的统一配置为准。

如需调整统一配置，应通过项目正常配置流程生成：

- 使用 Unity 菜单 `Bizza → Analytics Config` 生成 `BizzaAnalytics.bytes`；
- 按验收需要配置 `reporting_ratio` 和 `verbose_log`；
- 不得直接编辑加密 `.bytes` 文件；
- 不得修改 SDK 源码来强行打开日志。

如果统一配置且 `reporting_ratio < 1`，出现
`bizza_state=Ready reporting_enabled=False` 或 `event_sampled_out` 可能只是正常采样结果，
不能据此判断业务调用错误；但该设备不适合进行网络上报验收。

## 4. 为什么 Editor 可以直接验收

当前底层 `BizzaAnalytics` 在 `UNITY_EDITOR` 环境中会在事件和用户属性入队后立即执行 Flush，
所以正常情况下，每次业务事件交给底层后，很快可以看到：

```text
[BizzaGameAnalytics] event_accepted ...
[BizzaGameAnalytics] event_handed_off ...
[BizzaAnalytics] track(user) event=...
[BizzaAnalytics] send(start) ...
[BizzaAnalytics] send(result) ... ok=True status=2xx
```

网络请求是异步的。体验完最后一个操作后，应继续保持 Play Mode 数秒，优先等到最后一个
`send(result)` 出现再停止运行。

启动漏斗不经过业务封装队列，预期链路为：

```text
[BizzaAnalytics] lifecycle_event=game_start accepted=True launch_id=...
[BizzaAnalytics] load_stage_event=game_load_stage_start accepted=True launch_id=... stage_id=... stage_name=user_profile
[BizzaAnalytics] load_stage_event=game_load_stage_complete accepted=True launch_id=... stage_id=... stage_name=user_profile
[BizzaAnalytics] lifecycle_event=game_load_complete accepted=True launch_id=...
[BizzaAnalytics] track(user) event=game_start
[BizzaAnalytics] track(user) event=game_load_stage_start
[BizzaAnalytics] track(user) event=game_load_stage_complete
[BizzaAnalytics] track(user) event=game_load_complete
[BizzaAnalytics] send(result) ... ok=True status=2xx
```

## 5. 用户需要做什么

用户只需要：

1. 等 AI 告知“日志监听和配置检查已就绪”。
2. 在 Unity 中进入 Play Mode。
3. 像正常玩家一样体验本轮希望验证的内容。
4. 完成最后一个操作后停留数秒，让网络请求返回。
5. 退出 Play Mode，并告知 AI“本轮体验完成”。

用户不需要打开测试按钮，不需要手写 ID，不需要调用 SDK，也不需要复制整份 Console。

未在本轮体验中进入的玩法只能标记为“未覆盖”，不能标记为失败。若要覆盖提现、广告收益、
失败结算等特定路径，用户需要在游戏中真实触发对应行为。

## 6. 建议的自然体验路径

不要求用户严格照脚本点击，但一轮完整验收建议自然覆盖：

1. 启动游戏并进入主界面。
2. 打开并关闭一个关键页面。
3. 开始并完成一个关卡。
4. 正常消耗一次道具。
5. 正常请求并观看一次广告，等待 impression 和 revenue 回调。
6. 打开提现页面；测试环境允许时完成一次真实测试提现请求和结果。
7. 返回主界面并等待数秒。
8. 正常退出 Play Mode。

胜利、失败和主动退出是互斥的关卡结果。如果希望分别验证，需要进行多次关卡体验。

## 7. 各业务行为的预期事件

| 用户行为 | 预期事件/属性 |
|---|---|
| 启动游戏（任何加载前） | `game_start` |
| 各加载阶段开始 | `game_load_stage_start` |
| 各加载阶段完成或失败 | `game_load_stage_complete` |
| 全部加载完成并可进入游戏 | `game_load_complete` |
| SDK 会话启动 | `user_install`（首次）、`app_start`、`session_start`、初始用户属性 |
| 首次有效激活 | `user_activate` |
| 完成教程 | `tutorial_complete` |
| 打开/关闭页面 | `page_open`、`page_close` |
| 消耗道具 | `item_use` |
| 开始关卡 | `level_start` |
| 关卡胜利 | `level_win`、`level_duration` |
| 关卡失败 | `level_fail`、`level_duration` |
| 主动退出关卡 | `level_quit`、`level_duration` |
| 广告加载结果 | `ad_load` |
| 尝试播放广告 | `ad_show_request` |
| 广告确认开始播放 | `ad_show` |
| 广告展示回调 | `ad_impression` |
| 广告收益回调 | `ad_revenue` |
| 进入提现阶段 | `withdrawal_stage_enter` |
| 发起提现 | `withdrawal_request` |
| 提现后端结果 | `withdrawal_result` |
| Pause/Quit | `session_end` 及累计用户属性 |
| 性能采样周期到达 | `fps`、`lag_state` |

安装、激活和教程等一次性事件不会保证每轮重复出现。AI 必须结合本地状态和本轮实际体验判断，
不能因为非首次运行没有 `user_install` 就判定失败。

## 8. 关键关联关系

AI 不仅要统计事件数量，还要检查关联 ID：

### 8.1 关卡

- `level_start` 必须包含非空 `attempt_id`。
- `level_win`、`level_fail` 或 `level_quit` 必须使用同一个 `attempt_id`。
- 每个 `attempt_id` 最多只能有一种关卡结果。
- 对应 `level_duration` 应使用相同 `attempt_id`。

### 8.2 广告

- 广告 SDK 能提供稳定唯一 ID 时，同一展示实例的 `ad_impression` 和 `ad_revenue` 应使用相同
  `impression_id`；无法提供时跳过 impression，revenue 可以不带该字段。
- 提供 `impression_id` 时，同一个 ID 的 impression 和 revenue 各接受一次。
- 收益必须来自真实 revenue 回调，不能把 eCPM 当作 `revenue`。
- `event_rejected` 如果显示重复 `impression_id`，AI 应定位是否为广告 SDK 重复回调或业务重复接入。

### 8.3 提现

- `withdrawal_request` 和 `withdrawal_result` 使用相同 `request_id`。
- 金额和币种应一致。
- 成功结果必须发生在真实后端确认之后。
- 重复结果应被拒绝或由服务端最终幂等处理。

### 8.4 页面和会话

- `page_open` 和 `page_close` 的页面名一致。
- `page_close.duration_seconds` 不为负数。
- `session_start` 和 `session_end` 的 `session_id` 一致。
- Pause/Resume 不应造成同一会话重复结束。

### 8.5 游戏进入漏斗

- 单次 Play Mode 只接受一个 `game_start` 和一个 `game_load_complete`。
- 所有阶段事件与启动、最终完成事件的 `launch_id` 必须一致。
- 每个 `game_load_stage_start` 必须有相同 `stage_id`、`stage_name`、`stage_order` 的完成事件。
- `stage_duration_ms` 必须大于或等于 0；`success=false` 时应有稳定 `failure_reason`。
- 并行阶段允许顺序交叉，但不能共用 `stage_id`；重试必须产生新 ID。
- 只有开始没有完成的最后阶段，是本轮优先排查的加载中断位置。
- `game_load_complete.load_duration_ms` 必须大于或等于 0。
- 存在未完成阶段时不得接受 `game_load_complete`；玩家确实进入游戏但没有最终完成事件时判定接入失败。

## 9. 日志位置和读取范围

Windows Unity Editor 的完整日志通常位于：

```text
%LOCALAPPDATA%\Unity\Editor\Editor.log
```

当前 Windows 用户的绝对路径可通过 PowerShell 得到：

```powershell
$editorLog = Join-Path $env:LOCALAPPDATA 'Unity\Editor\Editor.log'
```

AI 应从最后一次包含以下文本且 `accepted=True` 的行开始分析，避免混入以前的 Play Mode：

```text
[BizzaAnalytics] lifecycle_event=game_start
```

如果本轮完全没有该日志，优先检查：

- 完整 SDK 是否已复制并成功编译；
- 当前代码是否实际进入 Play Mode；
- Console 普通日志是否被关闭；
- 日志是否来自另一台机器或另一个 Unity 实例。

AI 读取日志时只保留以下前缀：

```text
[BizzaGameAnalytics]
[BizzaAnalytics]
```

不要在验收报告中复制完整 Payload、UID、Player ID、配置地址、响应正文或其他可能敏感的值。
报告只保留事件名、状态、计数、必要关联 ID 的脱敏摘要和 HTTP 状态码。

## 10. 日志判定规则

### 10.1 初始化通过

必须看到：

```text
bizza_state=Ready reporting_enabled=True
```

SDK 没有公开初始化接口，初始化验收只以 `bizza_state` 和底层错误日志为准。

以下情况不通过网络验收：

- `bizza_state=Disabled`；
- `bizza_state=Failed`；
- 长时间停留在 `Loading`；
- `reporting_enabled=False`；
- 初始化错误中出现配置缺失、解密失败或 App ID 错误。

### 10.2 业务触发通过

实际体验过的业务行为必须出现对应 `event_accepted`。如果没有：

- 先确认用户是否真的走过该业务路径；
- 再检查接入代码是否位于真实成功回调，而不是未执行分支；
- 不得通过在测试代码里直接补调一次来掩盖接入错误。

### 10.3 底层交接通过

每个 `event_accepted` 最终应有同名 `event_handed_off`。正常帧最多交接一个事件，所以短时间内
允许有延迟。退出前仍未出现时，检查：

- 初始化是否 Ready；
- 是否发生 `submission_failed`；
- 是否发生队列溢出或清理；
- 是否过早停止 Play Mode。

### 10.4 底层详细日志通过

开启 `verbose_log` 后，应看到同名：

```text
[BizzaAnalytics] track(user) event=<event_name>
```

如果已有 `event_handed_off` 但没有底层详细日志，先确认统一配置是否真的开启 `verbose_log`，
不能直接判定底层没有接收。

### 10.5 网络请求通过

必须看到对应运行期间的成功结果：

```text
[BizzaAnalytics] send(result) ... ok=True status=200
```

任意 2xx 状态都可作为请求成功证据。以下情况需要记录失败原因：

- `ok=False`；
- HTTP 4xx/5xx；
- `send(build_failed)`；
- `send(retry)`；
- 长时间只有 `send(start)`，没有 `send(result)`。

一个批次可能包含多条事件，所以不能仅按 `send(result)` 数量和事件数量做一一对应。AI 应结合
`batch`、`records`、事件入队顺序和时间范围判断。

## 11. 常见非故障情况

- 没有 `user_install`：可能不是首次安装或本地已记录成功。
- 没有 `user_activate`：可能设备已经激活，或本轮没走到激活业务点。
- 没有 `fps/lag_state`：体验时间未达到性能采样周期。
- 出现 `event_sampled_out`：当前设备被采样排除，应在统一配置中将 `reporting_ratio` 调整为 `1.0`。
- `event_accepted` 和 `event_handed_off` 有数帧间隔：封装正常帧每帧最多交接一个事件。
- `send(result)` 少于事件数：底层按批次发送，不是一事件一请求。
- 没有底层 `track(user)`：统一配置可能关闭了 `verbose_log`。
- 强制停止进程缺少最终 `session_end`：系统未触发生命周期回调时无法完全保证。

## 12. AI 输出报告格式

AI 完成分析后按以下格式输出：

### 12.1 本轮结论

- 初始化：通过 / 失败 / 未验证
- 业务触发：通过 / 部分覆盖 / 失败
- 底层交接：通过 / 部分失败 / 未验证
- 网络请求：通过 / 失败 / 因 verbose_log 或网络原因未验证
- 后台入库：已人工核对 / 未核对

### 12.2 事件覆盖表

| 事件 | 本轮是否实际体验 | accepted | handed_off | 底层 track | 成功批次 | 结论 |
|---|---|---:|---:|---:|---:|---|

结论只能使用：

- `通过`：体验过且证据链满足本轮验收层级；
- `失败`：体验过但出现明确错误或证据链中断；
- `未覆盖`：本轮没有体验对应玩法；
- `条件不足`：缺少 verbose 日志、网络或后台权限。

### 12.3 关联检查

- 启动漏斗 `launch_id` 和 `load_duration_ms` 检查；
- 加载阶段 `stage_id`、名称、顺序、结果和阶段耗时检查；
- 关卡 `attempt_id` 配对结果；
- 广告 `impression_id` 配对结果；
- 提现 `request_id` 配对结果；
- 页面和会话配对结果；
- 重复和拒绝事件摘要。

### 12.4 异常摘要

只列出：

- 初始化失败；
- `event_rejected`；
- `submission_failed`；
- 队列溢出或清理；
- `send(build_failed)`；
- `send(retry)`；
- `send(result) ok=False`；
- 已体验但完全没有事件的业务路径。

每个异常需要提供本轮日志中的简短证据、影响和最小排查方向，不要提出过度设计方案。

## 13. 可直接交给 AI 的验收提示词

```text
请按照以下文档分析本次 Unity Editor 正常游戏体验产生的打点日志：

Assets/BizzaAnalytics/BizzaGameAnalytics/编辑器体验验收文档.md
Assets/BizzaAnalytics/BizzaGameAnalytics/AI接入文档.md

本次先只做日志分析，不修改代码。

从 Windows 的 `%LOCALAPPDATA%\Unity\Editor\Editor.log` 中找到最后一次
`[BizzaAnalytics] lifecycle_event=game_start accepted=True`，只分析该位置之后的本轮日志。仅关注
`[BizzaGameAnalytics]` 和 `[BizzaAnalytics]` 前缀。

分别验证：
1. game_start 是否在最早期被接受；
2. 自动初始化是否进入 Ready 且 reporting_enabled=True；
3. 各加载阶段 start/complete 是否按 stage_id 配对，launch_id 是否一致，顺序、结果和耗时是否有效；
4. 玩家完成全部加载后，game_load_complete 是否被接受，且与 game_start 的 launch_id 相同、
   load_duration_ms >= 0；
5. 用户实际体验过的普通业务行为是否产生 event_accepted；
6. accepted 的普通业务事件是否最终出现同名 event_handed_off；
7. verbose_log 开启时是否出现对应底层 track(user)；
8. 是否出现 send(result) ok=True 且 HTTP 状态为 2xx；
9. 是否存在 event_rejected、submission_failed、队列溢出、send(build_failed)、send(retry)
   或 send(result) ok=False；
10. attempt_id、impression_id、request_id、页面和 session_id 是否正确配对；
11. 没有体验到的功能标记为“未覆盖”，不能判定失败；
12. 不得把 lifecycle_event/load_stage_event accepted、event_accepted 或 event_handed_off 描述为服务器已收到。

报告不得输出完整 Payload、UID、Player ID、配置地址、响应正文或其他敏感值，只输出事件名、
计数、必要关联 ID 的脱敏摘要和 HTTP 状态码。

按文档第 12 节格式输出结论、事件覆盖表、关联检查、异常摘要和尚未验证内容。如果找不到
本轮 game_start 日志，直接说明无法划定本轮日志范围，并要求重新进入一次 Play Mode。
```

## 14. 最终通过标准

一次 Editor 体验可以判定“本轮日志验收通过”，需要同时满足：

- 初始化进入 `Ready` 且 `reporting_enabled=True`；
- `game_start` 与 `game_load_complete` 各接受一次、`launch_id` 一致且总加载耗时非负；
- 本轮真实加载阶段均正确配对，没有未知、重复或仍未结束的 `stage_id`；
- 用户实际体验的业务行为均产生正确原子事件；
- 关键事件 ID 关联正确且没有异常重复；
- 已接受事件正常交给底层；
- 开启底层详细日志时可以看到对应 `track(user)`；
- 网络环境允许时至少看到一个 `send(result) ok=True status=2xx`；
- 没有 `submission_failed`、队列溢出和明确发送失败。

该结论只覆盖本轮实际体验路径。未体验的广告类型、提现结果、关卡失败/退出等仍需后续体验
或专项测试，不能仅凭一轮正常玩法推断全部通过。
