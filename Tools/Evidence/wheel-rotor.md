Source: the current checked-in original assets and the arm64 reverse dump under
`C:/Projects/Nut Sort Relax/reconstruction/mumu-current`. No historical screenshot
was used to author or verify this change.

## Source and execution evidence

* `ReferenceOriginal/Res/ViewPrefabs/UIWheelView.prefab`, SHA-256
  `e523d1b40b8eebb39206db2378c3a44dd34ae6cab04e0d2ffaa8985f4b40c5cc`.
* `ReferenceOriginal/Res/Prefabs/WheelItem.prefab`, SHA-256
  `121fed5e6a2bed5756525fe9919b644ace9ba0349dac7b8fa82a807b479e884f`.
* `UIWheelView.OnInit`, RVA `0x23dd508`: obtain eight WheelItem instances from
  the configured pool, parent each under Items[i], set anchored position to zero,
  retain them in `objs`. Do not recreate them on every show.
* `OnBeforeShow`, `0x23dd774`: read the cached wheel map, draw
  `RandomWheelWeight` once, assign `WheelResultIndex`, initialize all eight items.
  This draw precedes the entrance animation and automatic spin delay.
* `StartSpin`, `0x23de19c`: request `wheelSpin`, set **all three** local Euler
  angles to zero, rotate local Z to `-45 * resultIndex - 360 * extraRotations`.
  The source uses FastBeyond360, so intermediate turns must not be reduced to
  the shortest arc. Prefab values are duration **2**, extra rotations **5**, ease
  **9 (OutCubic)**. The constructor's 5-second fallback is not the prefab value.
* `OnSpinComplete`, `0x23de46c`: read type and configured reward at completion,
  then call PlayEnd. Amounts are not frozen at the weighted selection.
* `WheelItem.Init`, `0x23dda04`: Cash means Coin active/Cash inactive for A,
  reversed for non-A; only the active amount text is refreshed using the existing
  CurrencyUtils formatting. This does not redefine the current language.
  Major uses sprite[1], Mini sprite[2], Grand sprite[0]; hide both money groups,
  show jackpot image and call SetNativeSize. Index 6 alone sets local rotation
  to +90 degrees (`ELF 0xdbc558 = pi/2`). Other indices retain their rotation.
  The original jackpot image quaternion is **-90 degrees**, even though its
  serialized Inspector Euler hint says +90. Preserve the quaternion.
* Source Roll RectTransform `224733206282342372`: size 828x828, anchored
  position (0,-268), eight 100x100 anchors on a radius-268 circle, local
  rotations increasing by 45 degrees. The original slight float errors are
  retained in the imported YAML.

## Implementation

`BuildWheelRotor.Save` copies the original WheelItem and exact Roll subtree;
it remaps scripts to native Unity Image/TMP and the recovered controller, and
sprite references to already imported original textures. It retains the original
font/material, colors, sizes, anchors, pivots, rotations and child ordering.
Unresolved GUIDs cause authoring to fail. Source files remain unchanged.

`RecoveredWheelRotor` uses Unity's ObjectPool and the configured WheelItem
prefab for the same eight initial instances. Prepare reuses them. The curve is
the exact cubic Hermite representation of `1-(1-t)^3`; Update advances it using
scaled delta time, writes the full rotation and reports the live type/reward.
There are no per-frame allocations, component searches, layout construction or
third-party tween/pool assemblies. The rotor does not award player balances.

## Validation

`RecoveredWheelRotorTests` instantiates the actual saved prefabs, checks both
cash/coin presentations and both currency format branches, original anchor
geometry, sprite sizes, font references and the special icon rotation. It tests
all eight weighted selections, one-draw RNG consumption, live reward lookup,
rotation reset, scaled-time pause, all 16 samples across each two-second spin,
exactly one completion and that the winning wedge ends at the top. Repeated
Prepare calls retain the same eight item instances.

The first full run `Artifacts/wheel-rotor-tests.xml` passed all 313 pre-existing
tests; its new test exposed an incorrect test expectation that the jackpot image
started at zero rotation. Inspection of both source and imported quaternions
confirmed -90, so only that test expectation was corrected. The focused rerun
`Artifacts/wheel-rotor-focused-tests.xml` then passed 1/1. Runtime and prefabs
were unchanged between these runs.

Fresh 1080x1920 renders were generated by that passing test and inspected:
`Artifacts/current-wheel-rotor-us.png` and
`Artifacts/current-wheel-rotor-alternative.png`. These show **only the rotor**,
with test reward values; the second capture independently selects A and the BR
format to exercise both inputs. It is not a claim that A implies Brazil, nor
evidence that the whole Wheel window or lifecycle is complete.

## Remaining Wheel integration

The full window, frame/pointer animation, jackpot meters/events, delayed
autostart and actual reward popup/cash-flight flow are now implemented and tested
in `wheel-window.md`. Free entry and production routing remain incomplete.
`Prepare` and `StartSpin` remain separate entry points for the native ordering.

Native evidence used by that window:

* DelaySpin MoveNext `0x23dee54`: wait .5 scaled seconds after OnAfterShow,
  then StartSpin.
* PlayEnd MoveNext `0x23df1fc`: cash requests `wheelWin`; jackpot sets task(2,1),
  requests Sound1 `ring`, maps Grand->JakpotWinType1, Major->2, Mini->3 and
  dispatches the jackpot event. Both frame and pointer play `win`, wait 1 second,
  then kill the selected item's transform tweens and start its scale pulse.
* Pulse return callback `0x23de8a0`: scale back to 1 in .3 seconds, then
  `0x23de9b8`. That callback hides Wheel and opens UIRewardView for cash;
  jackpots read the **current player jackpot balance** (Grand +0x4c, Major +0x50,
  Mini +0x54), stop Sound1 and open UIJackpotView. Do not substitute the
  wheel-config amount for the actual jackpot balance.
* ELF RELA + script metadata resolves `0x4f1ec60` -> `wheelSpin`,
  `0x4f1ecb8` -> `wheelWin`, `0x4f1d328` -> `win`, `0x4f1d258` -> `ring`,
  `0x4f1d2e0` -> ShowWindow<UIRewardView>, `0x4f1d240` -> ShowWindow<UIJackpotView>.

Do not treat the decompiler's tail after another known method entry as part of
the enclosing function. Global pool ownership across window destruction and
offscreen tween lifetime also need review when the complete window is bound.
SDK behavior is unchanged.
